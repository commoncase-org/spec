## Introduction

### Scope

This specification defines **commoncase**, an unambiguous,
deterministic standard for converting software identifiers (such as
variable, function, class, and field names) into canonical casing
representations: PascalCase, camelCase, snake_case, kebab-case, and
CONSTANT_CASE. This specification covers input normalization,
delimiter and orthographic tokenization, case folding, and
serialization into the five target styles, alongside an immutable
standard lexicon for compound morphemes. This specification does not
address natural-language text processing, sentence grammatical
segmentation, multi-identifier prose extraction, or locale-dependent
linguistic inflection.

### Pipeline Architecture

Processing is governed by a strictly monotonic, four-stage pipeline:
Normalization, Tokenization, Case Folding, and Serialization.
Execution order is invariant: each stage consumes the exact output of
its predecessor. No stage may be skipped, reordered, or executed
conditionally, except as permitted under Conformance Classes and
Profiles.

## Conformance and Terminology

### Requirements Language

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",

### Conformance Classes and Profiles

This specification defines two orthogonal axes of conformance:
**Conformance Classes** (governing output serialization capabilities)
and **Conformance Profiles** (governing input character validation and
delimiter tolerance).

#### Conformance Classes

1. **Class A (Full Transformation Engine):** An implementation
   conforms to Class A if and only if it implements all four pipeline
   stages (Normalization, Tokenization, Case Folding, Serialization),
   supports all five Serialization styles defined in Serialization, and
   produces output matching every normative test vector in Annex A for
   its supported Profile(s).
2. **Class B (Targeted Serializer):** An implementation conforms to
   Class B for a designated subset of serialization styles if and only
   if it implements Normalization, Tokenization, Case Folding, and the
   designated styles, producing output matching all corresponding test
   vectors in Annex A for its supported Profile(s).

#### Conformance Profiles

Conforming implementations MUST declare support for at least one of
the following two profiles:

1. **Strict Profile (Strict commoncase):**
   - The character repertoire following Normalization MUST consist
     strictly of alphanumeric characters (`ALPHANUM`) and explicit
     delimiters (`DELIM`).
   - The processor MUST terminate execution and reject any input
     containing characters outside this repertoire with an
     `InvalidCharacterError`.
   - Recommended as the standard profile for compilers, AST
     manipulators, code generators, and schema deserializers.
2. **Basic Profile (Basic commoncase):**
   - The processor operates permissively by extending delimiter
     classification under Rule D1-B.
   - Any contiguous sequence of characters outside `ALPHANUM` is
     treated as a delimiter boundary.
   - Recommended for search indexing, user-facing CLI inputs, and
     forgiving text sanitization.

Conformance is evaluated exclusively on **externally observable
behavior** (black-box input-to-output mapping). Conforming
implementations are free to use any internal architecture, execution
optimization, or state-machine representation, provided the observable
output is bit-for-bit identical to the transformations specified
herein.

### Terminology

The following load-bearing terms are used throughout this
specification with the meanings defined here:

- **Token**: An ordered, non-empty sequence of alphanumeric
  characters representing an atomic segment of an identifier.
- **Boundary**: A zero-width split position between two adjacent
  characters, or a position indicated by one or more delimiters, at
  which Tokenization divides an input string into distinct Tokens.
- **Delimiter**: An explicit non-alphanumeric separator character
  (hyphen, underscore, space, dot, or forward slash) that demarcates
  boundaries. Delimiters are never part of any Token.
- **Permissive Delimiter**: In the Basic Profile, any character
  outside `ALPHANUM` (including ASCII punctuation, symbols, and
  whitespace) that demarcates a boundary under Rule D1-B.
- **Strict Identifier**: An identifier whose post-normalization
  representation consists exclusively of `ALPHANUM` and `DELIM`.
- **Orthographic Signal**: A structural feature within an unpunctuated
  character run—such as a transition between character cases or
  between letters and digits—that indicates a Boundary.
- **Delimiter-Free Run**: A maximal contiguous substring that
  contains no Delimiter characters.
- **Cap-Run**: A maximal contiguous sequence of two or more ASCII
  uppercase letters.
- **Standard Core Lexicon**: The immutable, normative dictionary
  (Annex C) that maps specific compound substrings to designated token
  sequences before Case Folding runs.

## Syntax and Repertoire

### Character Model and Encoding

Input strings MUST be represented as sequences of Unicode scalar values
encoded in UTF-8 [RFC3629]. Prior to segmentation, input strings MUST
be normalized to Unicode Normalization Form C (NFC) per [UAX15] to
resolve canonical equivalence between precomposed and decomposed
character sequences.

### Formal Grammar (ABNF)

The core syntax of commoncase identifiers, tokens, and serialization
styles is formally specified using Augmented Backus-Naur Form (ABNF)
per [RFC5234]:

```abnf
UPPER           = %x41-5A                  ; ASCII A-Z
LOWER           = %x61-7A                  ; ASCII a-z
ALPHA           = UPPER / LOWER            ; ASCII letters
DIGIT           = %x30-39                  ; ASCII digits 0-9
ALPHANUM        = ALPHA / DIGIT            ; Alphanumeric character

; Strict delimiters
DELIM           = %x2D / %x5F / %x20 / %x2E / %x2F
                                           ; - _ SP . /

; Non-alphanumeric ASCII symbols and punctuation
ASCII-SYMBOL    = %x21-2C / %x3A-40 / %x5B-5E / %x60 / %x7B-7E
                                           ; ! " # $ % & ' ( ) * + ,
                                           ; : ; < = > ? @ [ \ ] ^ ` { | } ~

; Basic profile delimiters (strict delimiters + symbols + whitespace)
BASIC-DELIM     = DELIM / ASCII-SYMBOL / %x09 / %x0A / %x0D
                                           ; includes HTAB, LF, CR

token           = 1*ALPHANUM               ; Atomic token
strict-ident    = *DELIM [token *(1*DELIM token)] *DELIM
basic-ident     = *BASIC-DELIM [token *(1*BASIC-DELIM token)] *BASIC-DELIM
```

## Pipeline Specification

### Normalization and Character Validation

Normalization transforms Unicode input strings into US-ASCII octet
sequences and enforces profile validation prior to Tokenization:

1. **Pre-Normalization**: The processor MUST normalize the input
   string to Unicode Normalization Form C [UAX15].
2. **Transliteration**: The processor MUST replace every non-ASCII code
   point matching an entry in the Normative Transliteration Table
   (Annex B) with its designated ASCII replacement sequence.
3. **Universal Security Check**: If the string contains Unicode
   bidirectional formatting controls (e.g., `U+202A` through `U+202E`,
   `U+2066` through `U+2069`) or default-ignorable code points, the
   processor MUST reject the input with a `SecurityValidationError`.
4. **Profile Character Validation**:
   - **Strict Profile**: If the post-transliteration string contains
     any non-ASCII code point not defined in Annex B, the processor MUST
     reject the input with an `UnsupportedCharacterError`. If the string
     contains any ASCII character outside `ALPHANUM` and `DELIM` (such
     as `@`, `#`, `$`, `%`, `&`, `+`, `=`, control codes, or symbols),
     the processor MUST terminate execution and reject the input with
     an `InvalidCharacterError`.
   - **Basic Profile**: Non-ASCII code points present in Annex B are
     transliterated. Any remaining character outside `ALPHANUM` (whether
     ASCII punctuation, symbol, whitespace, or unmapped Unicode code
     point) MUST be treated as a `BASIC-DELIM` in Tokenization.
5. **Upstream Pre-Processing & Unicode CLDR**:
   - Core commoncase MUST NOT perform heuristic or hardcoded symbol
     transliterations into natural-language words (such as converting
     `@` to `"at"`, `&` to `"and"`, or `+` to `"plus"`).
   - Applications requiring semantic verbalization of symbols MUST
     perform such transformations as an upstream pre-processing step
     prior to invoking Strict commoncase. Applications MAY utilize
     Unicode CLDR localized character annotations [CLDR] or
     domain-specific translation dictionaries.
6. **Postcondition**: After Normalization, the intermediate string
   processed by Tokenization MUST consist strictly of US-ASCII
   characters (`%x00-7F`).

### Tokenization

Tokenization divides a Normalized input string into an ordered sequence
of Tokens in two steps: Delimiter and Orthographic Segmentation,
followed by Standard Core Lexicon application.

#### Delimiter Segmentation (Rules D1 and D1-B)

- **Rule D1 (Strict Profile Delimiter Boundary)**:
  Any contiguous sequence of one or more `DELIM` characters (`-`, `_`,
  space, `.`, `/`) MUST be treated as a Boundary. All `DELIM`
  characters MUST be discarded and MUST NOT be emitted into any Token.
  Leading and trailing delimiters MUST be stripped without creating
  empty tokens.
- **Rule D1-B (Basic Profile Generalized Delimiter Boundary)**:
  In the Basic Profile, any contiguous sequence of one or more
  `BASIC-DELIM` characters (any character outside `ALPHANUM`) MUST be
  treated as a Boundary. All `BASIC-DELIM` characters MUST be
  discarded and MUST NOT be emitted into any Token. Leading and
  trailing delimiters MUST be stripped without creating empty tokens.
  If the input contains no `ALPHANUM` characters, Tokenization yields an
  empty sequence of tokens (`[]`).

#### Orthographic Boundary Rules (Rules T1–T5)

Within each Delimiter-Free Run, boundaries are identified by the
following rules, evaluated in order:

- **T1 (Lower-to-Upper)**: A transition from an ASCII lowercase letter
  (`LOWER`) to an ASCII uppercase letter (`UPPER`) MUST be treated as a
  Boundary.
  *(Note: `"userId"` splits to `"user"` and `"id"`.)*
- **T2 (Cap-Run Termination)**: In a Cap-Run immediately followed by
  an ASCII lowercase letter (`LOWER`), a Boundary MUST be placed
  immediately before the Cap-Run's final letter, so that the final
  letter begins the subsequent token.
  *(Note: `"IPAddress"` splits to `"ip"` and `"address"`.)*
- **T2a (Lone Uppercase Letter)**: A single uppercase letter preceded
  by a lowercase letter does not constitute a Cap-Run and is governed
  by Rule T1 alone.
  *(Note: `"xCoordinate"` splits to `"x"` and `"coordinate"`.)*
- **T3 (Letter-to-Digit Fusion)**: A transition from an ASCII letter
  (`ALPHA`) to an ASCII digit (`DIGIT`) MUST NOT be treated as a
  Boundary; the digit sequence fuses onto the preceding letters.
  *(Note: `"Sha256Hash"` fuses `"sha"` with `"256"`.)*
- **T4 (Digit-to-Upper)**: A transition from an ASCII digit (`DIGIT`)
  to an ASCII uppercase letter (`UPPER`) MUST be treated as a Boundary.
  *(Note: `"Sha256Hash"` splits before `"Hash"`.)*
- **T5 (Digit-to-Lower Fusion)**: A transition from an ASCII digit
  (`DIGIT`) to an ASCII lowercase letter (`LOWER`) MUST NOT be treated
  as a Boundary; the lowercase sequence fuses onto the preceding digit.
  *(Note: `"top10items"` yields single token `"top10items"`.)*

#### Delimiter-Free Runs

A Delimiter-Free Run containing no orthographic signal matching Rules
T1–T5 MUST default to a single Token. This default MUST NOT be
overridden by heuristic dictionary segmentation; it MAY be overridden
only by an explicit match in the Lexicon.

#### Standard Core Lexicon Processing

The Standard Core Lexicon (Annex C) is an immutable registry of
domain-specific token substitutions. After orthographic boundaries are
placed, candidate tokens are compared case-insensitively against the
Lexicon:

1. If a candidate token matches an entry in the Standard Core
   Lexicon, the candidate token MUST be replaced with the ordered token
   sequence prescribed by that entry.
2. Lexicon replacement MUST occur before Case Folding runs.

### Case Folding

Case Folding transforms each Token into a normalized case form:

1. **Titlecase Transformation**: For every style except `constant`,
   Case Folding MUST uppercase the first letter of each Token (if an
   ASCII letter) and lowercase all subsequent letters in that Token.
2. **Uniformity**: This rule MUST apply uniformly to every Token,
   including two-letter acronyms, multi-letter acronyms, and tokens
   produced by the Lexicon. No length exception is permitted.
3. **Digit Invariance**: ASCII digits within a Token remain unmodified.

### Serialization

Serialization combines the folded Token sequence into the requested
target style according to the normative synthesis matrix below:

| Style | Initial Token Casing | Subsequent Tokens Casing | Inter-Token Delimiter | Example (`user`, `id`) |
| :--- | :--- | :--- | :--- | :--- |
| **Pascal** | Capitalized | Capitalized | None | `UserId` |
| **camel** | Lowercase | Capitalized | None | `userId` |
| **snake** | Lowercase | Lowercase | `_` (`%x5F`) | `user_id` |
| **kebab** | Lowercase | Lowercase | `-` (`%x2D`) | `user-id` |
| **constant** | Uppercase | Uppercase | `_` (`%x5F`) | `USER_ID` |

Empty Token sequences evaluate to the empty string across all styles.

## Security Considerations

### Collision Hazards and Non-Invertibility

Transformation through commoncase is a non-injective ($N \to 1$)
projection: multiple distinct input strings inevitably map to identical
token sequences and serialized outputs (e.g., `userId`, `user_id`, and
`user-id` all serialize to `user_id`).

- **Identifier Collisions**: Systems MUST NOT use commoncase output as
  unique primary keys in security-critical contexts, such as user
  identity tokens, authorization role identifiers, or access-control
  predicates.
- **Mass Assignment in APIs**: API gateways and object-relational
  mapping (ORM) deserializers MUST NOT automatically bind incoming
  parameters to internal model properties after commoncase
  canonicalization without verifying that parameters do not collide
  with administrative attributes.

### Algorithmic Complexity and ReDoS

Implementations MUST execute all pipeline stages in $O(N)$ linear time
relative to input length. Implementations MUST NOT use backtracking
regular expression engines capable of exponential complexity (ReDoS)
when implementing Rule T2 or delimiter tokenization. Tokenization MUST
be executed via deterministic finite automata (DFAs) or single-pass
linear character scanners.

### Resource Exhaustion and Input Bounds

Conforming implementations MUST enforce a maximum input length bound.
The default maximum limit MUST NOT exceed 256 Unicode scalar values
(or 256 UTF-8 bytes). Inputs exceeding this limit MUST be rejected with
a `PayloadTooLargeError` prior to Normalization, preventing memory
exhaustion attacks.

### Unicode Security and Trojan Source

Implementations MUST reject inputs containing Unicode bidirectional
formatting control characters (e.g., `U+202A` through `U+202E`, `U+2066`
through `U+2069`) to mitigate Trojan Source attacks [CVE-2021-42574].
Default-ignorable and unassigned code points MUST be rejected.

### Locale-Independent Invariant Casing

Case Folding and Serialization MUST operate using invariant ASCII
table lookups, independent of host operating system or runtime locale
settings (preventing Turkish dotless-i casing anomalies).

## Versioning, Stability, and Evolution Strategy

### Semantic Versioning

This specification conforms to Semantic Versioning (SemVer 2.0.0):

- **MAJOR** version increments indicate breaking changes that alter the
  output of previously valid inputs, modify pipeline execution order,
  or modify entries in the Standard Core Lexicon.
- **MINOR** version increments indicate backward-compatible additions
  (e.g., new serialization styles or non-breaking profiles).
- **PATCH** version increments indicate non-normative editorial
  clarifications.

### Lexicon Epoch Model

Because persistent datastores (database schemas, protobuf schemas, ORM
bindings) depend on permanent identifier stability, the Standard Core
Lexicon (Annex C) is an immutable artifact within a major release.
Entries in the Standard Core Lexicon MUST NOT be added, modified, or
removed in minor or patch releases.

### User-Defined Lexicon Extensions

Implementations MAY support user-defined domain lexicons via an
explicit configuration parameter. User-defined lexicons take precedence
over the Standard Core Lexicon but MUST NOT alter default behavior in
standard conforming mode.
